## 2.2 Critical 级问题

### C-01: pc-mall前端LoginView错误处理分层不完整
- **严重程度**: Critical
- **影响范围**: 功能级 - 登录模块
- **发现位置**: [pc-mall/src/views/LoginView.vue](file:///home/tailor/Tailoris/tailor-is-frontend/pc-mall/src/views/LoginView.vue#L337-L345)
- **问题描述**: 登录错误处理中，503/服务不可用场景仅做了`return`跳过，未区分401/503/账号错误三种场景。虽然已通过request.ts拦截器分层处理了HTTP状态码，但LoginView组件内的catch块仍保留了"账号或密码错误"的统一提示，可能与拦截器弹窗产生双重弹窗。
- **复现步骤**: 输入错误密码登录 → 观察弹窗数量
- **建议方案**: 移除LoginView中所有catch块的ElMessage.error调用，完全依赖request.ts拦截器的分层处理；或确保LoginView中仅处理业务层特定错误。

### C-02: merchant-admin LoginView未区分错误类型
- **严重程度**: Critical
- **影响范围**: 功能级 - 商家登录模块
- **发现位置**: [merchant-admin/src/views/LoginView.vue](file:///home/tailor/Tailoris/tailor-is-frontend/merchant-admin/src/views/LoginView.vue#L357-L359)
- **问题描述**: `handlePasswordLogin`中catch块直接`ElMessage.error('账号或密码错误，请重新输入')`，未区分401/503/网络错误等场景。
- **复现步骤**: 模拟MySQL宕机登录 → 仍提示"账号或密码错误"
- **建议方案**: 实现与pc-mall一致的分层错误处理。

### C-03: platform-admin LoginView未区分错误类型
- **严重程度**: Critical
- **影响范围**: 功能级 - 平台管理登录模块
- **发现位置**: [platform-admin/src/views/LoginView.vue](file:///home/tailor/Tailoris/tailor-is-frontend/platform-admin/src/views/LoginView.vue)
- **问题描述**: 同merchant-admin，catch块统一提示"账号或密码错误"。
- **建议方案**: 同C-02。

### C-04: .env.example中端口配置与v4.0规范严重不一致
- **严重程度**: Critical
- **影响范围**: 系统级 - 部署配置
- **发现位置**: [.env.example](file:///home/tailor/Tailoris/.env.example#L61-L77)
- **问题描述**: .env.example中的端口变量定义与v4.0规范文档和docker-compose.services.yml实际配置完全不一致。例如：GATEWAY_PORT=9000（正确）但LITE_GATEWAY_PORT=9001（应为8081），USER_PORT=8080（应为8101），ADMIN_PORT=8082（应为8100）等。这是旧版端口方案的残留。
- **复现步骤**: 查看.env.example第61-77行
- **建议方案**: 立即更新.env.example中的端口配置，与RoutePortConstant.java和docker-compose.services.yml保持一致。

### C-05: frontend.conf与frontend-docker.conf的Core Gateway路由路径不一致
- **严重程度**: Critical
- **影响范围**: 系统级 - Nginx路由
- **发现位置**: 
  - [frontend.conf](file:///home/tailor/Tailoris/deploy/nginx/frontend.conf#L172)
  - [frontend-docker.conf](file:///home/tailor/Tailoris/deploy/nginx/frontend-docker.conf#L172)
- **问题描述**: frontend.conf的Core Gateway路由正则仅匹配了user|auth|product|favorite|order|cart|payment|settlement|account|sandbox|marketing|coupon|points|seckill|ai|body-size|copyright|merchant|shop|admin|pattern，而frontend-docker.conf则额外包含了design|knowledge|trade|data|edu|fabric。两者路由规则不一致，可能导致部分API路由行为差异。
- **复现步骤**: 对比两个文件第172行
- **建议方案**: 统一两个配置文件的路由规则，以v4.0规范文档为准。

## 2.3 High 级问题

### H-01: 全局异常处理器缺少DataSourceConnectException处理
- **严重程度**: High
- **影响范围**: 系统级 - 异常处理
- **发现位置**: [GlobalExceptionHandler.java](file:///home/tailor/Tailoris/tailor-is/tailor-is-common/src/main/java/com/tailoris/common/exception/GlobalExceptionHandler.java)
- **问题描述**: 根据项目规范，需要区分DataSourceConnectException（数据库/Redis连接失败，返回503），但当前GlobalExceptionHandler中未定义该异常处理器。数据库连接失败会被RuntimeException或Exception兜底处理为500，无法向前端返回503以区分"服务不可用"。
- **建议方案**: 在GlobalExceptionHandler中新增`@ExceptionHandler(DataSourceConnectException.class)`方法，返回HTTP 503。

### H-02: RoutePortConstant中端口定义与实际部署不一致
- **严重程度**: High
- **影响范围**: 系统级 - 端口规范
- **发现位置**: [RoutePortConstant.java](file:///home/tailor/Tailoris/tailor-is/tailor-is-common/src/main/java/com/tailoris/common/constant/RoutePortConstant.java#L90-L117)
- **问题描述**: RoutePortConstant.java中merchant-service的端口定义为8110，但docker-compose.services.yml中merchant-service也在core-trade分组使用core-service（端口8110）。同时，RoutePortConstant中design-service=8116、knowledge-service=8117的端口定义与docker-compose.services.yml一致，但与v4.0规范文档中pattern-service=8115、design-service=8116一致。整体对齐良好，但部分服务在规范文档中归入不同分组（如pattern-service在compose中属于core-ai-chain但端口8115在轻量段）。
- **建议方案**: 统一RoutePortConstant、docker-compose.services.yml和v4.0规范文档三方的端口分类。

### H-03: CoreGatewayRouteConfig包含/dashboard路由但未在v4.0规范中列明
- **严重程度**: High
- **影响范围**: 模块级 - 网关路由
- **发现位置**: [CoreGatewayRouteConfig.java](file:///home/tailor/Tailoris/tailor-is/tailor-is-core-gateway/src/main/java/com/tailoris/coregateway/config/CoreGatewayRouteConfig.java)
- **问题描述**: CoreGatewayRouteConfig中未包含dashboard相关路由，但v4.0规范文档中dashboard路由归lite-gateway的analytics-service处理。当前配置正确。
- **建议方案**: 确认状态正常，无需修改。

### H-04: 前端VITE_API_BASE_URL配置不一致
- **严重程度**: High
- **影响范围**: 功能级 - 前端API调用
- **发现位置**: 
  - [pc-mall/.env.development](file:///home/tailor/Tailoris/tailor-is-frontend/pc-mall/.env.development#L1) - VITE_API_BASE_URL为空
  - [merchant-admin/.env.development](file:///home/tailor/Tailoris/tailor-is-frontend/merchant-admin/.env.development#L1) - VITE_API_BASE_URL=/api/v1
  - [platform-admin/.env.development](file:///home/tailor/Tailoris/tailor-is-frontend/platform-admin/.env.development#L1) - VITE_API_BASE_URL=/api/v1
- **问题描述**: pc-mall的VITE_API_BASE_URL为空字符串，而merchant-admin和platform-admin为`/api/v1`。这意味着pc-mall在生产环境可能依赖不同的baseURL配置方式。
- **建议方案**: 统一所有前端项目的VITE_API_BASE_URL配置策略。

### H-05: 部署脚本中缺少中间件健康等待逻辑
- **严重程度**: High
- **影响范围**: 系统级 - 部署流程

- **问题描述**: 根据部署文档要求，中间件（MySQL/Nacos/Redis）未就绪前必须阻塞业务微服务启动。docker-compose已配置depends_on+healthcheck，但dev-start.sh脚本中是否包含足够的等待时间需要验证。
- **建议方案**: 在dev-start.sh中增加中间件健康状态显式检查步骤。

### H-06: trim兼容性问题
- **严重程度**: High
- **影响范围**: 模块级 - 前端

### H-07: 前端项目缺少统一的错误处理中间件

## 7.3 部署步骤

```bash
# 步骤1: 环境准备
cd /home/tailor/Tailoris
```

## 7.4 回滚机制

### 回滚触发条件
1. 部署后核心服务（gateway/user/order）健康检查失败
2. 登录链路回归测试失败
3. 数据库迁移失败
4. 端口冲突导致服务无法启动

### 回滚步骤
```bash
# 1. 停止当前所有服务
docker compose -f docker-compose.services.yml --profile "*" down

# 2. 恢复数据库备份
# 使用 restore-mysql.sh 脚本

# 3. 切换到上一个稳定版本镜像
# 修改 docker-compose.services.yml 中的镜像标签

# 4. 重新启动服务
docker compose -f docker-compose.services.yml --profile core-trade up -d

# 5. 执行回归测试
```
